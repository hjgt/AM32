# S4N: second positioning vector retains duty

## Evidence

S4M-LITE stopped capture: hardware-backups/S4M-LITE-read-rJwtMz/capture.json.
12 completed trials (user estimated 11); trials 1–11 reached software handoff
and finished on operator zero. Trial 12: zero qualified acquisition edges,
15 acquisition timeouts, no handoff, NO_LOCK at the acquisition deadline.
No COMM_LATE or closed-loop feedback timeout in this run. Filtered current
at completion was 106 centiamps, not peak phase or peak battery current.

Trials 5/8/9 first qualified edges occurred around 201–203ms, with 10 timeout
steps and handoff around 306–318ms. A handoff is not independently measured
mechanical synchronization. Zero qualified edges does not prove zero motion.

## One experimental control change

Old positioning: vector 1 ramps request 210→360 over 10ms then holds to 30ms;
vector 2 drops to 210 and repeats the same ramp/hold. Both PWM request and
alignment cap use this ramp, so the second drop is an actual command change.

S4N keeps vector 1 unchanged; vector 2 requests 360 throughout its 30ms.
Hypothesis: avoid weakening excitation just when changing the positioning
vector. This is not a measured torque controller or a confirmed root cause.
It may instead increase the positioning jerk/current; bench comparison required.
Peak commanded duty is unchanged, but mean drive during vector 2 increases.

Unchanged: physical vector order in both directions, 60ms total alignment,
360ms total acquisition bound, first-sector 30ms wait, subsequent deadlines,
one-shot rescue budget, request 400 in acquisition, duty cap 610, first-five
edge timing, sixth-edge handoff, JEOS/24kHz PWM, EEPROM, all stop conditions.
32-result lightweight recorder retained, no per-sample waveform logging.

Opt in with:
`FD6288_ALIGN_HOLD=1 FD6288_DIAGNOSTICS=0 FD6288_PIN_SCAN=0 FD6288_PIN_SYNC=0 node tools/scripts/build_fd6288_s4j.cjs alignnative`

Default remains old alignment; separate obj-startup-S4J-alignnative-hold folder.
Trace variant 34. Runtime light-log ABI stays 1; use matching packaged ELF.
No automatic flashing or GitHub upload. Runtime finite-recapture policy is
still pending and must not be confused with this startup-only experiment.

## Verification and next test

Host tests cover both directions, exact dwell/deadline, DWT wrap, first-vector
ramp, constant second-vector duty, ignored alignment edges, real-edge handoff,
fresh start reset, clean/logged modes, and old/new alignment flags. Scheduler
tests retain late/cancel/zero/fault behavior. Main-only HEX boundary check required.

Compare approximately 15 starts using the same throttle as the last run,
return to zero and let the rotor stop between starts, note failed trial IDs.
Keep power for stopped SRAM capture. Stop the test if kicks/heating worsen;
do not compensate by increasing throttle. Compare late first-edge/handoff and
zero-edge failure counts, not just the overall percentage of one small batch.
